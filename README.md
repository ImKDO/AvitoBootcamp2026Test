# Кандидатогенерация для поиска услуг Авито

Для каждого запроса бенчмарка выбираем из 189 212 объявлений до 50 кандидатов.
Условие — в [TASK.md](TASK.md).

**Результат на локальной валидации:** Recall@50 = **0.942** (12 208 запросов, 5-fold CV),
≈ **0.932** после поправки на состав бенчмарка. Всё работает на CPU, `answer.csv`
собирается с нуля за ~5 минут и при повторном запуске совпадает побайтно.

```bash
uv sync
uv run avito-predict   # → answer.csv
uv run avito-cv        # оценка качества
```

Данные положить в `data/` (архив по ссылке из TASK.md). Промежуточные результаты
кэшируются в `cache/`, его можно удалить — результат не изменится.

## Как устроено

1. **Пул кандидатов** (~310 на запрос, в пул попадает 97.8% нужных объявлений).
   Сигналы считаются сразу против всего корпуса, в пул идёт объединение топов:
   основная смесь сигналов (топ-300), BM25 без учёта локации (топ-20),
   расширение запроса с учётом локации (топ-50).
2. **LightGBM** выбирает из пула финальные 50 по 39 признакам. Ансамбль из трёх сидов.

## Данные и признаки

- **Train — это логи, а не разметка для корпуса.** Объявления из train почти не
  пересекаются с корпусом (~5%), поэтому train используется как история поиска:
  что искали и что выбрали.
- **Локация — главный сигнал.** 83% кликов приходятся на ту же локацию, где искали.
  По логам строится `P(локация объявления | локация поиска)`: так поиск по области
  или стране раскладывается по городам. Плюс расстояние в км до объявления.
- **Слова исполнителя, а не пользователя.** Для запроса ищем до 20 похожих запросов
  в логах и берём, что по ним выбирали: распределение микрокатегорий и слова из
  заголовков выбранных объявлений (расширение запроса). Отдельно — микрокатегории
  по фильтрам поиска.
- **Текст:** BM25 по заголовку, параметрам и описанию (веса 1 / 0.5 / 1). Описание
  важно: только по заголовку — 0.66, по трём полям — 0.86. Стемминг Snowball.
- **Объявление:** рейтинг, отзывы, цена, полнота описания, скрыт ли телефон.
  Помогает выбрать из десятка одинаковых объявлений то, которое реально выбирают.
- **Не используются:** `search_is_delivery_search` (почти всегда 0) и
  `search_category` (в бенчмарке у 9% запросов 0, в train такого нет).

## Как проверялось качество

Train делится на две части:
- **knowledge** (465 тыс. строк) — объявление не из корпуса. Отсюда берутся все
  статистики по логам;
- **labelled** (12 208 запросов, по одному на текст) — пользователь кликнул
  объявление из корпуса. Ищем по всему настоящему корпусу и проверяем, нашлось ли оно.

Ответы валидации никак не попадают в статистики, реранкер оценивается out-of-fold
с фолдами по тексту запроса.

Бенчмарк сложнее валидации: незнакомых логам запросов 65% против 28%, без фильтров — 63%
против 34%. Поэтому recall дополнительно перевзвешивается по этим стратам
(колонка «под бенчмарк»).

| Шаг | Recall@50 | под бенчмарк |
|---|---|---|
| BM25 по полям | 0.41 | |
| + приор локации | 0.86 | |
| + микрокатегории и расширение из логов | 0.90 | 0.89 |
| **+ реранкер LightGBM** | **0.942** | **0.932** |

Не вошло: жёсткий фильтр по локации (0.69 против 0.83 у мягкого приора), тюнинг
LightGBM (±0.0005), эмбеддинги `multilingual-e5-large` (+0.9 п., но 2.5 часа на
кодирование корпуса и нестабильность fp16 на разном железе, а нужен точно
воспроизводимый `answer.csv`).

## Ошибки и что с ними сделано

Разобраны промахи реранкера: ~2% нужных объявлений не попадают в пул, ~5% оказываются
ниже 50-го места.

- **Объявление в другом городе** («губы модель» ищут в одной локации, выбирают в Москве).
  Среди промахов своя локация у 57% против 81% в среднем. → Мягкий приор вместо
  фильтра, расстояние как признак, источник BM25 без локации.
- **Пользователь и исполнитель пишут по-разному** («аренда помещения на праздник» →
  «Пространство для мероприятий»). → Расширение запроса и микрокатегории из логов,
  BM25 по описанию.
- **Много одинаковых объявлений**, выбрано одно из десятков («психолог», «инженер пто»).
  Во многом неустранимо. → Признаки «привлекательности» объявления.
- **Размытые запросы** («ремонт», «метро теплый стан»). → Приор по фильтрам поиска,
  признаки неуверенности (энтропия микрокатегорий, близость к логам).

## Код

```
src/avito_candgen/
├── data/                 # данные
│   ├── load.py           #   чтение parquet
│   ├── split.py          #   train → логи (knowledge) и валидация (labelled)
│   └── text.py           #   нормализация, стемминг, токены корпуса
├── candidates/           # ступень 1: пул кандидатов
│   ├── bm25.py           #   BM25 по полям
│   ├── location.py       #   модель локаций
│   ├── search_logs.py    #   похожие запросы из логов: микрокатегории, расширение
│   ├── features.py       #   признаки объявления и запроса
│   └── generator.py      #   сигналы → отбор кандидатов → признаки
├── ranking/              # ступень 2: реранкер
│   ├── reranker.py       #   LightGBM, топ-50
│   └── validation.py     #   Recall@K, CV, поправка на бенчмарк
├── pipeline.py           # сборка всего вместе, кэш пулов
└── cli.py                # avito-predict, avito-cv
```

Формат `answer.csv`: `query_id`, `answer` — до 50 `item_id` через пробел, по убыванию
уверенности.
